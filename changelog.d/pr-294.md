### Added
- `lium provider node list`, `node get`, `node status` and `lium provider status` print a red BLOCKING panel for each node that is kept off the listing or out of idle pay: every reason with its measured and required value and `Fix: <what to do>`, then the Secure listing requirements the node does not meet. The node table shows such a node as `BLOCKED` instead of a green `AVAILABLE`, and `lium provider status` counts the blocked nodes at the top.
- `--json`: each node carries the same list under `blocking_reasons` (`node status` adds it to the verification object, `status` adds `blocked_node_count`). The CLI shows the portal's `blocking_reasons` as served; until the portal serves them it builds the list from the validator's last error, the listing's hidden reasons and the idle-pay reasons, and marks those nodes `"blocking_reasons_source": "cli_fallback"`.
- An idle-pay reason that Secure listing does not require (the GPU model is outside the idle-pay program, or there is no idle-pay room for the node's size) is not a blocker: `node get` and `node status` print it as `Not eligible for idle pay: <reason>` with a `No action: <why>` line, `node list` and `lium provider status` print a short dim marker per node, and `--json` lists it in `blocking_reasons` with `"gating": false`. It never counts as blocked.
- The BLOCKING panel prints the portal's `fix_command` on its own line under `Fix:` and the `docs_url` as `Docs: <link>`. The portal's `secure_requirement` decides which reasons are listed as unmet Secure requirements. A partly rented host whose free GPUs are unlisted (`WHOLE_HOST_ONLY`, `SPLIT_MINIMUM_NOT_MET`) is not blocked. `node list --miner-hotkey <your own hotkey>` reads the idle-pay reasons like `node list` does.
- Whether a reason blocks is the portal's `gating` when the portal serves it. Otherwise the CLI uses its legacy list of gating codes, and says so: an entry the portal sends without `gating` (an older portal) is decided from its code and marked `"gating_source": "cli_legacy_fallback"`, and while the portal sends no `blocking_reasons` at all the CLI builds them itself and marks the node `"blocking_reasons_source": "cli_fallback"`. The panel also prints the portal's `requires` (`Requires: sudo · reboot`) and `verify_command` (under `Verify:`).
- A reachability or last-error reason (`kind` `availability` or `last_error`) gets the BLOCKING panel and counts as blocked whatever its `gating`; only an idle-pay reason with `gating: false` prints as not eligible for idle pay.
- `lium provider node get|status --fail-on-blocked` exits 10 when the node has a gating reason; under `--json` the one envelope is `{"ok": false, "error": {"code": "node.blocked.<reason code>", "exit_code": 10, "data": <the result>}}`. `node status --watch --until-clear [--timeout N]` stops with exit 0 once the node is clear and exits 10 at the timeout. Plain `--watch` is unchanged; with `--fail-on-blocked` it exits 10 at the first refresh that finds the node blocked.
- `lium provider --json` errors go to stdout as `{"ok": false, "error": {"code", "legacy_code", "message", "hint", "exit_code", "context", "data"?}}`. `code` is namespaced snake_case (`portal.not_found`, `input.arg_invalid`, `auth.expired`, …), and `legacy_code` keeps the old UPPER_CASE code (`null` for `node.blocked.*`, which has none). Every provider error, `node.blocked.*` included, carries `legacy_code` and `context` (`{}` when empty). Exit statuses are unchanged. `LIUM_OUTPUT=json` has the same effect as `--json` on every `lium provider` command.
- SDK: `ProviderClient.provider_overview()` (`GET /miners/overview`).
- Codes in the `node.blocked.<code>` envelope never hold a space: a last error the portal sends without `reason_code` is `node.blocked.last_error`, with its text in `message`. Any other code that is not one token becomes its ASCII slug plus 8 hex digits of its sha256, so two codes never share a slug.
- `--json`: an entry the CLI builds from the validator's last error (on a `cli_fallback` node) carries `"kind": "last_error"`, like the portal's own entries.
- A reason the CLI builds itself (a `cli_fallback` node) carries `requires` for the codes the portal catalog knows: `sudo`, `reboot` and `no_rentals` for the driver and profiling fixes, `sudo` and `no_rentals` for sysbox, disk and a power cap under sysbox, `sudo` for too few ports, none for the rest. A code the catalog does not know (the validator's last error, a hidden reason) gets `requires: []` with `"requires_unknown": true`: hand it to a person.
