### Fixed
- `@lium.machine`: arguments travel as a pickle (your own bytes, loaded on your own pod) and the result comes back as a JSON envelope plus an `.npz` sidecar for numpy arrays, read with `allow_pickle=False` — nothing the pod writes is unpickled on your machine (the file comes from provider hardware). What round-trips, exactly: `None`, `bool`, `int`, `float`, `str`, `bytes`; `list`, `tuple`, `set`, `frozenset`, `dict` of those, nested; `datetime`/`date`/`time`/`timedelta`, `Decimal`, `pathlib.Path`, `uuid.UUID`; `numpy.ndarray` of any dtype without Python objects (any shape, structured and datetime64 included) and numpy scalars, each as its own type. Anything else — a dataclass, an `Enum`, an `OrderedDict`, a tensor, an ndarray subclass — is a `lium.ResultEncodingError` raised on the pod that names the type and where it sits in the result, re-raised here (return `.tolist()`, `dict(x)`, `x.value` instead). Before, a numpy argument was `NameError: array` and a numpy result `TypeError: not JSON serializable`, after the GPU work was paid for. An exception raised on the pod is re-raised with its own type when that type is a builtin (`except ValueError` works; its args come along when they are plain data, else its message); other types arrive as `RemoteExecutionError` with the name. Either way its `__cause__` is the new `lium.RemoteExecutionError` with `exception_type`, `remote_traceback`, `exit_code`, `stdout`, `stderr`. The shipped source is the bare `def` (decorators and annotations removed, dedented), so methods, nested functions, `async def` and `np.ndarray` annotations run. A function that closes over variables or uses module-level names (imports, constants, helpers) is refused when decorated, with the names listed, instead of failing with `NameError` on the pod a minute and a few cents later.
